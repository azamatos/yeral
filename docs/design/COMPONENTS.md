# Ýeral Web — component map · design system v0.5 (16–17.10.2026)

**What this is.** The repo already has a design system in code: `@yeral/ui` (38 components, `packages/ui`) with Storybook 10 (`apps/storybook`, storybook.yeral.app), built from DS v0.3.1 (`screens/system/Main.dc.html`, `DS-Components.dc.html`, `DS-Booking.dc.html`). Since then the full client site and the whole business workspace were designed (rounds 3–6). They introduced new components, variants, badges and patterns. DS v0.5 collects them, picks one canonical version of each, and maps every one to code. **The Storybook must grow with every new screen: no screen ships a component that has no stories.**

**Sources (read with this file)**
- `screens/system/DS-Patterns.dc.html` — "DS · Product components · v0.5": domain-free primitives and the new variants of existing `@yeral/ui` components → Part 1.
- `screens/system/DS-Business.dc.html` — "DS · Business patterns · v0.5": domain components (calendar, requests, clients, team, settings, access & accounts, reviews, notifications, analytics, landing, tables, classes, client-site cards, phone) → Part 2.
- `tokens.css` v0.5 — v0.3.1 plus aliases for values the screens already used (Part 3, `token-audit.md`).
- Each drawing on the boards has a grey caption: `Name · package · Storybook: … · from: <screens>`. The caption and the row here say the same thing.

**Round 6 in one breath (16–17.10.2026):** everything free on MVP (billing components retired) · one Ýeral login with several workspaces → WorkspaceSwitcher, AccountMenu, LoginFlow, InviteCard, ProfileDrawer · fixed access levels → PermissionMatrix, AccessLevelField, role variants of calendar/analytics · "who answers requests" → RequestHandlingSetting · statuses → StatusBadge icons (dot retired), StatusLegend, InternalStatusChip, StatusSettings, `--ring-selected` · phones → BottomTabBar, MoreSheet, QuickBookingSheet, phone-first NewBookingDrawer · **part B (client logic gaps)** → StatusBadge canceller sub-lines, OfferedTimes, Price (hidden / "-den"), ChangeSummary, move-mode Stepper, phone-only call card, owner preview banner, unverified page, undo-failed toast, party chips with a limit, BookingLinkCard, MoveRequest, CombinedTableSuggestions, SpecialDayOverlapWarning. Details: "Round 6 changes" at the top of Part 1 and Part 2.

**Rules for Claude Code**
1. Before building a screen, look up every piece of it here. Status `exists` → use it. `extend` → add the listed variant/prop **and its stories** first. `new` → create it first: domain-free → `@yeral/ui` via `pnpm gen ui-component <name>`; domain → the FSD place in the row (`entities/*/ui`, `features/*/ui`, `widgets/*`), with stories in the same slice. `retired` / `remove` → don't build it (or delete it if it exists).
2. Build from the board, not from older screen markup: where screens drifted, the board holds the winner (drift lists below). Screens keep their layout and copy; components come from the boards.
3. Stories: one per variant and state on the board (default, hover, focus-visible, selected, disabled, loading, error, empty, long text, phone width), one per access level for permission-driven components, a `Playground`, `play` tests for keyboard + pointer, axe. The story file names its board and section.
4. No text inside components (labels/aria from props or i18n keys; design copy is Turkmen, the owner checks it during coding). Values only from `tokens.css`. Domain-free components never import from entities.
5. Primitive ownership: if a domain component on DS-Business contains a primitive that DS-Patterns also draws (StatusBadge, BottomTabBar, NumberStepper, Checklist, CopyField, Pill, TimerPill, Stepper variants, SaveBar, WorkspaceSwitcher, AccountMenu…), the DS-Patterns primitive is the one to build; the domain component composes it.

**Suggested order**
1. Tokens v0.5 → `theme.css` + `tokens.test.ts`.
2. Shell primitives: SideNav (rail 72, access-level items), WorkspaceSwitcher, AccountMenu, BottomTabBar + MoreSheet, AppTopBar, StatusBadge (icons), StatusLegend; then Button (danger-ghost, on-ink, FAB), Input/Field (sizes, warning/success, counter), Chip, Table, Drawer/Modal, Toast.
3. Login: PhoneInput, CodeInput states, AuthCard → domain LoginFlow, InviteCard.
4. New primitives: Pill, TimerPill, DeltaPill, Callout, SaveBar, SettingsLayout/Group/Row, InputGroup, CopyField, NumberStepper, TimeRangeField, Combobox, TagInput, Accordion, ProgressBar/Meter, Checklist, Timeline, StatTile, KeyValueList, AvatarStack, Kbd, PhotoManager, MapFrame, QrBlock, SwatchPicker, IconPicker; charts with Analytics.
5. Domain, in screen order: Business/Calendar (CalendarGrid, BookingBlock, ScheduleLayers, CalendarLegend, InternalStatusChip, Toolbar incl. role variants) → Requests & Bookings (phone-first NewBookingDrawer, QuickBookingSheet) → Access & accounts (PermissionMatrix, AccessLevelField, InviteRow, TransferOwnershipModal, ProfileDrawer) → Clients → Onboarding & Settings (RequestHandlingSetting, StatusSettings) → Services & Team → Reviews → Notifications → Analytics → Landing → Tables → Classes. Rules that apply to every row: Radix primitive where one exists + `cva` variants + `cn()`; no text inside components (all copy, aria-labels and live-region messages come in as props); values only from `tokens.css` v0.3.1 (see `token-audit.md` for the few proposed additions); scaffold with `pnpm gen ui-component <name>`; every story gets render + interaction + axe tests.

Storybook column: `exists — Title` = no change · `extend — Title: add …` = new variant / prop / story on an existing title · `new — Group/Title` = new component and stories · **retired** = drop the variant / story / example. Rules from part B that every component above follows:
- **One booking per declined request.** Taking an offered time creates at most one booking (declined → Tassyklandy at once; unanswered → a new request, Tassyklandy at an instant business); the old row keeps a link to the new code and its chips disappear. Offered times bypass the phone-only restriction (**phone-only exception**).
- **Undo window = 5 minutes.** “Yzyna al” exists for 5 minutes after a client cancel; it can fail (bu wagt eýýäm başga müşderä berildi · sapakda boş ýer galmady · ýazylyş wagty başlandy · haýyşyň jogap wagty gutardy) → one shared message + “Başga wagt saýla”.
- **No silent specialist swap.** A move (and a booking) keeps the chosen specialist; the time grid shows only that person’s free times, or anyone’s with “Islendik hünärmen”. (Rule change — today the code reassigns to another free specialist.)
- **A move keeps the original.** Until the business answers, the booking stays at its time (client badge Tassyklandy + pending line; calendar original + ghost). Declined / unanswered → stays; accepted → moves. Only appointments move; tables and classes cancel + rebook. Moving follows the free-change window (2 sagat öňünden).
- **Current-slot start, no back-dated bookings.** Staff may start a booking or reservation at the current slot (`slotNow = floor(now / step) × step`: 11:20 → 11:15, tables 18:40 → 18:30); nothing earlier today is offered — recording a past visit is later.
- **Mobile numbers only** for SMS codes (+993 6… / 7…); a link page never shows or edits the full phone.

Rules that apply to every row:
- **Layers.** `entities/*/ui` = read-only views of one entity (no mutations, no routing); `features/*/ui` = one user action with its own model (mutation, optimistic update, toast); `widgets/*` = compositions placed on pages. Business app slices sit in `apps/business`, client-site slices in `apps/web`; shared entities (booking, venue, review, service, staff, account) keep one `model` and two `ui` flavours where the sites differ. Phone auth (`features/auth-by-phone`) is shared by both apps — one Ýeral account.
- **Copy.** No literal text in components: labels, statuses, aria-labels and live-region messages come from i18n keys. Round 6 was designed in Turkmen only; keys stay ready for RU / EN (RU runs about 30 % longer — LongTextRU stories on BookingBlock, BookingRow, ResultRow, ServicePickRow).
- **Status tones + icons.** Only `--st-{pending|confirmed|completed|noshow|cancelled}-{bg,line,ink,dot}` from `tokens.css` v0.3.1, and one icon per system status (`statusesV2.system[].icon`). Status is never colour alone: icon + text in badges, icon on blocks, timer icon + number, strike for cancelled. Internal statuses (`statusesV2.internal`) are team-only, never change the system status and never reach the client site.
- **Permissions.** Three fixed access levels (Eýesi · Administrator · Hünärmen) + Programmasyz hünärmen (no login); permissions per level from `accessLevels.permissions` (true / false / "own" / "view"), edited in Rugsatlar. What a level can’t use is **hidden, not disabled** (menu items, columns, tiles, buttons) — the only disabled controls are read-only views of data the person can see (Administrator looking at Topar / Rugsatlar). Money renders only with revenue = all, or own money with revenue = own; components take `revenueScope: 'all' | 'own' | 'none'` and remove what is not allowed. Who may answer a request = workspace rule (`requestHandling`) ∧ per-person override; the owner always can.
- **Time.** All times are tabular numerals; positions on time grids are computed from minutes (`top = (start − from) × pxPerHour / 60 + 1`, `height = duration × pxPerHour / 60 − 2`).
- **Loading.** Skeletons copy the real geometry (`.sk` n-100, r6), appear after 300 ms, never a spinner for lists (States 08). Buttons show an inline spinner and keep their width.
- **Tests.** Every story gets render + interaction + axe tests; drag interactions also get a keyboard test; permission-driven components get one story per access level.
